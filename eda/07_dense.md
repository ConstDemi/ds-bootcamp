# 07 — Dense-ретривер (эмбеддинги)

Код: `src/dense.py` (кодирование, поиск all/geo, выгрузка), `experiments/dense_run.py` (замеры и кандидаты),
`experiments/dense_compare.py` (сравнение моделей и настроек на подкорпусе).
Запуск из корня репозитория:
```
python src/dense.py encode e5-small --max-seq 64          # корпус → work/emb/e5-small.npy (+_ids.npy, .json)
python experiments/dense_run.py --model e5-small --max-seq 64 --filters --save   # замеры + work/cands/dense_*.parquet
```

## Важно: GPU не было

В этой сессии CUDA недоступна: система загружена с ядром `7.0.0-34-generic`, а модуль `nvidia-595-open`
собран только для `7.0.0-28` и `7.0.0-31` (`modinfo nvidia` → not found, `nvidia-smi` падает).
Чинится загрузкой в ядро 7.0.0-31 или установкой `linux-modules-nvidia-595-open-7.0.0-34-generic` (нужен sudo).

Поэтому всё посчитано на CPU (6 потоков из 12, параллельно шёл расчёт BM25):
- модель **multilingual-e5-small**, `max_seq_length=64`, int8-квантизация линейных слоёв (`torch.ao.quantization.quantize_dynamic`);
- корпус 189 212 документов кодировался **1 192 с (~20 мин)**, ~160 док/с;
- запрос: 1.7 мс на кодирование + 0.7 мс поиск all / 0.8 мс поиск geo (CPU, батчами);
- пик RAM прогона `dense_run.py` — 3.9 ГБ.

Код сам выбирает устройство: на GPU — fp16 без квантизации. После починки драйвера достаточно
перезапустить `encode` с `--max-seq 256` и `dense_run.py --max-seq 256 --save` — это даст заметно лучшие эмбеддинги (см. ниже).

## Кандидаты для гибрида

`work/cands/dense_{val,bench}_{all,geo}.parquet`: query_id, item_id (str), score (float32, косинус), rank (int32, с 1).
Топ-300 на каждый запрос без повторов (val — 3 000 запросов, bench — 2 452).
В `geo` для городских запросов rank не монотонен по score: сначала идут объявления города, потом добор из всего корпуса.
Регионы бенчмарка берутся из `validation.region_location_ids()`, регионы валидации — из `is_region`.

## Выводы

1. **Главное из промахов:** в 7 из 10 случаев топ-3 релевантен запросу, часто точнее выбранного объявления. Ответ — одно из многих
   равнозначных объявлений, и выбор определяется не текстом, а географией, ценой, рейтингом или популярностью.
   Текстовая релевантность, которую дают эмбеддинги, почти исчерпана на уровне «нужная тема». Дальше помогут гео (особенно для регионов:
   маппинг регион → города по train) и ранжирование равнозначных кандидатов признаками объявления.
2. Два промаха — из-за жёсткого городского пула в маленьком городе: нерелевантные объявления города стоят выше релевантных из соседних.
   В среднем это почти не влияет (мягкий бонус +0.004), но гибриду стоит брать score, а не только rank из `geo`.
3. Потолок кандидатов: geo@300 = 0.84, то есть реранкер над топ-300 dense может поднять Recall@50 с 0.69 максимум до ~0.84.
4. Качество эмбеддингов недобрано из-за CPU (int8, 64 токена): на подкорпусе fp32 + 128 токенов дают ~+0.05 R@50. После починки GPU:
   перекодировать e5-small с `--max-seq 256` в fp16 (~несколько минут) и сравнить с `deepvk/USER-base` / `multilingual-e5-base`,
   если удастся скачать веса.

## GPU-пересчёт

CUDA заработала: RTX 3070 Laptop (8 ГБ), torch 2.14 cu130, sentence-transformers 6.1. Все модели считались в **fp16, `max_seq_length=256`**
(снижать seq не пришлось; батч корпуса 256 для e5-small, 128 для e5-base и USER-base, 64 для bge-m3, пик видеопамяти ~3 ГБ).
Запрос с дописанными значениями фильтров, как в лучшем CPU-варианте. Документ тот же, `item_text()`.
```
python src/dense.py encode bge-m3 --max-seq 256 --batch 64 --tag bge-m3_s256        # → work/emb/bge-m3_s256.{npy,_ids.npy,json}
python experiments/dense_run.py --model bge-m3 --tag bge-m3_s256 --max-seq 256 --filters --save
```

| модель (лицензия) | префиксы (по карточке) | dim | корпус, с | R@50 all | R@50 geo |
|---|---|---|---|---|---|
| e5-small, CPU int8 seq 64 (прежний) | `query: ` / `passage: ` | 384 | 1 192 | 0.310 | 0.690 |
| `intfloat/multilingual-e5-small` (MIT) | `query: ` / `passage: ` | 384 | **145** | 0.373 | 0.752 |
| `intfloat/multilingual-e5-base` (MIT) | `query: ` / `passage: ` | 768 | 354 | 0.370 | 0.738 |
| `deepvk/USER-base` (Apache-2.0) | `query: ` / `passage: ` | 768 | ~580 | 0.318 | 0.728 |
| **`BAAI/bge-m3` (MIT)**, dense-вектор (CLS) | нет | 1024 | 1 159 | **0.384** | **0.764** |

- Время корпуса — чистое кодирование без загрузки. У bge-m3 первые 3 куска из 23 шли параллельно с USER-base. USER-base кодировался в два захода (2 + 21 кусок): второй занял 531 с, на весь корпус это ~580 с.
- USER-base: sentence-transformers 6.1 не читает её `modules.json` (у Normalize `path=""`, падает на `config.json` трансформера).
  В `load_model` модули собраны вручную: трансформер + mean-pooling + нормировка, как в `1_Pooling`. Префиксы ставятся вручную, `prompt=""`.
- Запрос: 0.2–0.6 мс на кодирование (батч 128) и 0.1–0.2 мс на поиск all/geo по всему корпусу на GPU.

**Модель или железо.** Тот же e5-small на GPU (fp16, seq 256) даёт 0.690 → 0.752 geo, то есть +0.062. Почти весь прежний
недобор объясняется CPU-режимом (int8 и 64 токена), а не моделью. Смена модели даёт меньше: bge-m3 − e5-small = +0.012 geo
(парный бутстреп, 95% ДИ [+0.001; +0.024]). Более крупные e5-base и USER-base хуже e5-small: −0.014 и −0.024.
bge-m3 − e5-base = +0.027 [+0.016; +0.038], bge-m3 − USER-base = +0.036 [+0.024; +0.049].

**Выбрана bge-m3.** Она лучшая почти на всех срезах; на «с фильтром» и «у ответа есть история» идёт вровень с e5-small. Но кодирует корпус в 8 раз дольше e5-small (19 мин против 2.5 мин).
Если время важнее, e5-small s256 почти не уступает в гибриде (см. `08_hybrid.md`).
