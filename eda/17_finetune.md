# 17 — Дообучение модели эмбеддингов на парах «запрос → выбранное объявление»

Код: `src/ft_train.py` (пары, обучение), `src/ft_eval.py` (кодирование корпуса, dense-оценка, итоговый пайплайн, файлы кандидатов).
Итоговый пайплайн не менялся: `ft_eval.py` импортирует `geo_run.py` / `geo.py` / `rerank_meta.py` и повторяет схему geo2 + бонусы метаданных
с любым числом dense-источников в RRF.

Запуск из корня репозитория (env `avito_retrieval`):
```
python src/ft_train.py --name e5-small-ft --batch 256 --grad-ckpt                  # 9 мин, 3.0 ГБ VRAM
python src/ft_eval.py encode --name e5-small-ft --batch 256                        # корпус, 2.5 мин
python src/ft_eval.py dense  --name e5-small-ft --ref e5-small_s256 --ref bge-m3_s256
python src/ft_eval.py pipe   --name e5-small-ft --name bge-m3-lora --tag lora      # ~5 мин
python src/ft_train.py --name e5-small-ft-full --full-train --batch 256 --grad-ckpt  # модель для бенчмарка
python src/ft_eval.py encode --name e5-small-ft-full
python src/ft_eval.py final --name e5-small-ft --best bge+e5-small-ft_w --bench-name e5-small-ft-full
# вторая модель (LoRA, нужен peft):
python src/ft_train.py --model BAAI/bge-m3 --name bge-m3-lora --q-prefix "" --d-prefix "" \
       --lora 16 --lr 1e-4 --grad-ckpt --batch 128 --max-pairs 64000                 # 25.5 мин, 5.1 ГБ VRAM
python src/ft_eval.py encode --name bge-m3-lora --batch 64                         # 18.6 мин
```

Пакеты: для e5-small ничего нового не нужно (цикл обучения написан на torch, `SentenceTransformerTrainer` не используется,
потому что ему нужны `datasets` и `accelerate`). Для LoRA поставлен **peft 0.21.0**, он подтянул **accelerate 1.15.0**.
torch 2.14.0 и transformers 5.17.0 остались прежними.

## Данные и защита от утечки

- Пары строятся только по `train[train_mask]`: 493 897 строк. Строки 3000 отложенных запросов в обучение не попадают. Модель для бенчмарка (`e5-small-ft-full`) обучена по той же схеме на полном train.
- Запрос — `search_query` + значения фильтров, как `dense.query_text(with_filters=True)`. Документ — `text.item_text` **выбранного** объявления из той же строки train (item_* поля train), то же представление, что у корпуса.
- Убраны дубли пар (запрос с фильтрами, item_id): 493 897 → 458 021. На один нормализованный текст оставлено не больше 20 пар (случайных, seed 0): → **219 328 пар, 71 993 текста**. Без ограничения частые тексты («маникюр» — тысячи пар) заслонили бы хвостовые запросы, а бенчмарк в основном из них.
- Батчи без дублей (аналог `NoDuplicatesBatchSampler`): в одном батче не повторяются нормализованный текст запроса, item_id и текст документа. Иначе «негатив» был бы правильным ответом.

## Обучение

| | e5-small-ft | bge-m3-lora |
|---|---|---|
| основа | intfloat/multilingual-e5-small | BAAI/bge-m3 |
| что учится | всё (118 млн параметров) | LoRA r=16, α=32, dropout 0.05 на query/key/value/dense (7.1 млн), после обучения влита в веса |
| лосс | MultipleNegativesRankingLoss (in-batch negatives, косинус × 20) | то же |
| префиксы | `query: ` / `passage: ` | нет |
| длина | запрос 64, документ 128 токенов | то же |
| батч / lr / warmup | 256 / 3e-5 / 5%, линейный спад | 128 / 1e-4 / 5% |
| точность | fp32 мастер-веса + fp16 autocast, gradient checkpointing | основа fp16, адаптеры fp32, checkpointing |
| пары | все 219 328, 1 эпоха, 856 шагов | случайные 64 000, 499 шагов |
| лосс (первые / последние 50 шагов) | 2.27 → 0.86 | 1.11 → 0.62 |
| время обучения (RTX 3070 Laptop) | **9.0 мин** (+36 с на пары) | **25.5 мин** |
| пик VRAM | 3.05 ГБ | 5.14 ГБ |
| кодирование корпуса (seq 256, fp16) | **2.5 мин** | 18.6 мин (как у готового bge-m3) |

Gradient checkpointing обязателен: без него e5-small при батче 128 занимает 6.5 ГБ, почти всё — активации документов.
Лосс e5-small выходит на плато примерно к 200-му шагу (~50 тыс. пар), поэтому сокращение bge-m3 до 64 тыс. пар не должно было сильно навредить.
Все запуски сделаны с одним seed (0), разброс по seed не мерился.

## 2. В итоговом пайплайне: geo2 + бонусы метаданных

Схема прежняя, ничего не переподбиралось: sparse lemma+stem, правила Города SOFT_0.015 / регионы RSOFT_0.02 / 621540 RSOFT_0.005,
RRF k=60, бонусы base=score, Вид 0.003, Тип 0.0015, P(mc) 0.007, PRF 0.002. Классификатор микрокатегорий и гео-карты для валидации строятся по train[mask].
Вариант `bge` воспроизводит опорные числа точно: geo2 0.8581, + бонусы 0.8690.

Варианты источников:
- `ft` — BM25 + дообученный dense **вместо** bge-m3;
- `bge+ft` — три источника с весами 1/1/1 (dense перевешивает sparse 2:1);
- `…_w` — три источника с весами 1 / 0.5 / 0.5. Вес задан до эксперимента: сохраняется баланс sparse : dense = 1 : 1 и шкала RRF-скора, под которую подбирались гео-бонусы и бонусы метаданных.

Δ — к 0.869 на тех же запросах, парный бутстреп. **B** — отложенная половина (seed 0): на половине A подбирались веса бонусов метаданных (`11_meta_boost.md`), поэтому B — честная оценка. На B база 0.8659.

## 3. Выбор и файлы кандидатов

Выбран **`bge+e5-small-ft_w`**: BM25 + готовый bge-m3 + дообученный e5-small, веса RRF 1 / 0.5 / 0.5, дальше geo2 и бонусы метаданных без изменений.
По качеству он делит первое место с `bge-m3-lora`. Выбран по двум причинам:
1. Он лучший на главном срезе (без истории +0.012) и на регионах (+0.025). Интервал на B самый узкий.
2. Он в 3 раза дешевле для проверяющего: +9 мин обучения и +2.5 мин кодирования, 3 ГБ видеопамяти, новых пакетов нет. У LoRA 25 мин обучения на 64 тыс. парах, 5.1 ГБ VRAM и пакет peft.

Это решение принято с оглядкой на всю валидацию, не на A. Поэтому на B есть лёгкий оптимизм выбора, но все три лучших варианта дают на B одно и то же (+0.013…+0.014).

- `work/cands/hybrid_ft_val.parquet`: 3000 × 300, e5-small-ft обучен на train[mask], Recall@50 = 0.8844, @300 = 0.9538.
- `work/cands/hybrid_ft_bench.parquet`: 2452 × 300. Для бенчмарка e5-small переобучен по той же схеме на **полном** train (`e5-small-ft-full`, 222 325 пар). Карты и классификатор микрокатегорий тоже по полному train. Обучение шло 16 мин вместо 9, потому что GPU делили с другим процессом. Кодирование — 2.5 мин. Топ-50 совпадает с `hybrid_geo2_meta_bench` на 89.4%: переставлено ~5 из 50 мест. Для сравнения, бонусы метаданных меняли geo2 на 9.5%, LTR на 21%.
- Формат обоих файлов как у `hybrid_geo2_meta_*`: `query_id`, `item_id` (str), `score` (float32), `rank` (int32 с 1).

## Брать ли в финал

**Да, как замену кандидатам geo2 + бонусы: `bge+e5-small-ft_w`.** Прирост +0.015 на всей валидации, +0.014 [+0.007; +0.022] на отложенной половине и +0.012 на ответах без истории.
Он не завязан на популярность, поэтому ожидается и на платформе. Цена для проверяющего — около 12 минут GPU (обучение + кодирование корпуса) на RTX 3070 и никаких новых пакетов.
На CPU обучение нереально (часы), поэтому для CPU-режима пайплайна веса стоит приложить готовыми (470 МБ) или оставить этот шаг опциональным.

Что не сделано и риски:
1. **LTR поверх новых кандидатов не переучивался.** `ltr.py` строит признаки по `hybrid_geo2_*`. Эти кандидаты шире (@300 0.954 против 0.942), и LTR на них должен выиграть ещё. Это следующий шаг, отдельный прогон `ltr.py` на `hybrid_ft_*` с косинусом e5-small-ft как признаком. Эффекты частично пересекаются: оба поднимают правильные ответы в топ-50.
2. Интеграция в `src/pipeline.py` (флаг `--finetuned-dense`) не делалась: файл чужой. Нужно: обучить/загрузить `work/models/e5-small-ft*`, закодировать корпус, добавить третий список в RRF с весами 1/0.5/0.5 (`ft_eval.run_multi` / `rrf_weighted`).
3. Один seed обучения, гиперпараметры (lr, батч, cap=20, 1 эпоха) не подбирались. Hard negatives (например, из BM25-топа) не пробовались, они могли бы дать ещё.
4. 9% бенчмарка с `search_category = 0` (запросы вне услуг) в обучающих парах почти отсутствуют. На них дообученная модель может быть хуже готовой, и готовый bge-m3 в смеси это страхует. Это ещё один довод за вариант «третьим источником», а не «вместо».
