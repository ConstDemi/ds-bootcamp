# 11 — Бонусы за метаданные: фильтры и микрокатегория

Код: `src/rerank_meta.py` (функции), `src/rerank_meta_exp.py` (эксперименты).
Запуск из корня репозитория: `python src/rerank_meta_exp.py [--cands ... --bench ...]` (~3.5 мин, пик ~6.5 ГБ, только CPU).
Поверх geo2: `python experiments/rerank_meta_geo2.py`.
Скрипт экспериментов пишет `work/cands/hybrid_meta_{val,bench}.parquet`, сетку `work/meta_grid.csv`, итоговую таблицу `work/meta_report.csv`
и примеры `work/meta_examples.csv`.

## Главный результат: новые гео-кандидаты geo2

Кандидаты `work/cands/hybrid_geo2_{val,bench}.parquet` построены по новой гео-схеме: Recall@50 = **0.8581**, @300 = 0.942.
В их score уже заложен гео-бонус: RRF + 0.015 за свой город и 0.02 за крупные города региона.
Код: `experiments/rerank_meta_geo2.py` (~75 с). Выход: `work/cands/hybrid_geo2_meta_{val,bench}.parquet`.

Вектор весов выбранного варианта (Вид 0.003, Тип 0.0015, P(mc) 0.007, PRF 0.002) умножается на масштаб s.
Сравниваются две базы. Первая — `1/(60+rank)`: гео учтено только порядком. Вторая — исходный `score`: гео учтено величиной бонуса.
База и масштаб выбираются по половине A.

|---|---|---|---|---|---|
| rank, A / B | 0.8681 / 0.8679 | 0.8714 / 0.8658 | 0.8705 / 0.8638 | 0.8648 / 0.8558 | 0.8458 / 0.8421 |
| **score, A / B** | 0.8664 / 0.8654 | **0.8721 / 0.8659** | 0.8721 / 0.8684 | 0.8701 / 0.8664 | 0.8715 / 0.8644 |

Для сравнения база без бонуса: A 0.8611, B 0.8551.

**Выбрано по A: база score, s = 1.0.** На B: 0.8551 → **0.8659, Δ +0.011 [+0.004; +0.018]**. На всех 3000: 0.8581 → **0.8690**, Δ +0.011 [+0.006; +0.016].

## Постановка (эксперименты на старом гибриде 0.8023)

На входе топ-300 гибрида RRF (BM25 + bge-m3, geo) из `work/cands/hybrid_{val,bench}_geo.parquet`: Recall@50 = **0.8023**, @300 = 0.909.
Бонусы переставляют кандидатов только внутри этих 300. Новых id не добавляется, поэтому @300 не меняется.

Базовый скор равен `1/(60 + rank)`, а не исходному `score`. Так веса бонусов не зависят от шкалы конкретного ретривера,
и код работает на любом файле кандидатов. С исходным score результат почти тот же: 0.8144–0.8151 против 0.8161.
Масштаб: 50-е место стоит 1/110 ≈ 0.0091, 100-е 0.0063, 1-е 0.0164. Бонус 0.005 поднимает объявление примерно со 100-го места на 30-е.

**Защита от переподбора.** Валидацию (3000 запросов) делим на две случайные половины (seed 0). Все параметры выбираются
по половине A, а результат сообщается на половине B. Δ считается к базе на тех же запросах, 95%-интервал даёт парный бутстреп (2000 повторов).
База на B равна 0.7958: половина B немного труднее A (0.8088).

**Утечка.** Классификатор для валидации учится только на `train[train_mask]`, для бенчмарка на полном train.
Фильтровый бонус ничему не учится.

## Сигналы

**Фильтры.** Из `search_infm_params_text` берём «Вид услуги X», «Тип услуги X» и «Тип услуги автосервиса X» (последний
идёт в группу «Тип»). Значения «Другое» и пустые отбрасываем. Совпадение с объявлением проверяется подстрокой
«<ключ> <значение>» в `item_infm_params_text`. Несколько значений одного ключа трактуются как ИЛИ.
Значимый фильтр есть у 1043 из 3000 запросов валидации. Их правильные ответы совпадают по Виду в 97.8% случаев, по Типу в 97.0%, по обоим в 97.3%.
Среди кандидатов тех же запросов совпадают 66% из топ-50 и 43% с мест 51–300, то есть фильтр действительно отсеивает чужих.

**Микрокатегория.** Классификатор «текст запроса + значимые пары фильтра → `item_microcat_id`» (212 классов — все микрокатегории, встречающиеся в train; в корпусе их 752, но 212 покрывают 99.1% объявлений корпуса и 100% ответов валидации):
TF-IDF по словам 1–2 и char_wb 3–5 (по 100k признаков) + `SGDClassifier(log_loss, alpha=2e-6, 8 эпох)`, обучение ~30 с.
Строки train схлопываются в уникальные пары (документ, микрокатегория). Вес каждого уникального текста равен 1 и делится
между его микрокатегориями пропорционально числу выборов. Это имитирует бенчмарк, где на каждый текст один запрос.

| точность на валидации (верно, если микрокатегория любого правильного ответа) | top-1 | top-3 | top-5 | top-10 |
|---|---|---|---|---|
| **вес «по тексту» (выбран)** | **0.713** | **0.892** | 0.930 | 0.960 |
| — текста нет в train | 0.671 | 0.870 | 0.919 | 0.953 |
| — с фильтром / без фильтра | 0.847 / 0.635 | 0.956 / 0.854 | 0.968 / 0.908 | 0.986 / 0.945 |
| вес «по строкам» | 0.583 | 0.683 | 0.702 | 0.717 |
| alpha 1e-5 / 5e-7 / 20 эпох | 0.719 / 0.687 / 0.716 | 0.881 / 0.871 / 0.892 | | |

Вес «по строкам» проигрывает 13 п.п.: частые тексты (автосервис, маникюр) забивают хвост.

**PRF-микрокатегория (без обучения).** Бонус равен доле микрокатегории объявления среди топ-20 кандидатов того же запроса.

## Почему так

- **Фильтровый бонус работает только через «Вид»** и только на 35% запросов с фильтром: на них +0.018, на остальных 0 по построению.
  «Тип» отдельно ничего не даёт (+0.000). Тип есть у меньшей части запросов, а dense-канал гибрида уже получает строку фильтра в тексте запроса
  и хорошо её учитывает. Оптимум фильтрового веса (0.01) — это почти жёсткий фильтр. «Жёстко с запасом» 5 и 10 мест
  хуже, чем запас 0 (0.8041 и 0.7999 против 0.8068 на всех): 97% ответов совпадают с фильтром, и резервные места
  отнимают позиции 46–50 у совпадающих кандидатов, которые правильны чаще. Мягкий бонус равен квоте с запасом 0 или немного лучше неё.
- **Микрокатегория сильнее фильтра:** +0.016 против +0.007 на B. Она работает и у 63% запросов без фильтра (+0.012…+0.017),
  то есть у большинства бенчмарка. Вероятностный бонус лучше бонуса «в top-k»: уверенная модель (P ≈ 0.9) тянет сильно,
  неуверенная (P размазана) почти не вмешивается.
- **Фильтр и микрокатегория во многом дублируют друг друга.** Для запроса с фильтром «Вид» почти задаёт группу микрокатегорий,
  а классификатор получает фильтр на вход (top-1 на запросах с фильтром 0.85 против 0.64 без него). Поэтому в комбинации
  фильтровый вес падает с 0.01 до 0.003, и комбинация лишь немного лучше одной P(mc): +0.017 против +0.016 на B, разница в шуме.
- **PRF по топ-20 даёт +0.012 без всякого обучения.** Внутри топ-300 правильная микрокатегория и так преобладает наверху.
  В комбинации PRF немного поправляет случаи, где классификатор ошибается, но ретривер прав.
- **Большие веса вредят.** При w_mc ≥ 0.03 или «mc в top-1» с w = 0.01 Recall падает до 0.78: ответы из «соседней» микрокатегории
  улетают за 50-е место. Кривая по весу плоская в диапазоне 0.005–0.01 и круто падает дальше.

## Бенчмарк

Классификатор переобучен на полном train, фильтры разобраны из `benchmark_queries`, веса взяты те же.
Результат лежит в `work/cands/hybrid_meta_bench.parquet`: 2452 запроса по 300 кандидатов, топ-50 совпадает с исходным на 84%.
Оговорка: на бенчмарке у 9% запросов `search_category = 0` (вне услуг). Там классификатор, обученный на услугах, может ошибаться,
но вес P(mc) при неуверенной модели мал, так что заметного вреда ожидать не стоит.

## Как пользоваться

```python
import rerank_meta as rm
items = rm.load_items("data/benchmark_items.parquet")                     # item_id, params, microcat
model = rm.fit_microcat(train[train_mask])                                 # для бенчмарка — полный train
f = rm.filter_match(cands, queries, items)                                 # m_vid / m_tip / m_all
f = rm.microcat_prob(f, queries, items, model)                             # p_mc, mc_rank
f["prf"] = rm.prf_microcat(f, items, top=20).to_numpy()
new = rm.rerank_bonus(f, w_vid=0.003, w_tip=0.0015, w_mc=0.007, w_prf=0.002,
                      base="score")   # base="score", если в score уже есть гео-бонус (geo2); иначе base="rrf"
```

Нужные пакеты: scikit-learn и scipy (уже есть в окружении).

## Что дальше

1. Признаки `m_vid`, `m_tip`, `p_mc`, `prf` можно подать в обучаемый реранкер (LightGBM/логрег по парам) вместе с рангами источников.
   Аддитивный бонус с 4 весами — это его ручная линейная версия.
2. Классификатор можно усилить kNN по похожим запросам train или эмбеддингами bge-m3 запроса: top-1 0.71, top-3 0.89, запас есть.
3. Для пар смежных микрокатегорий (частая причина порчи) можно давать бонус не за точную микрокатегорию, а за её
   «кластер» — суммировать P по микрокатегориям, которые часто путаются в train.
